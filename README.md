# fluency-demo

A shareable AI-fluency demo: landing → passcode → intake ("how do you want this to go?") → personalized plan → diagnostic → calibration result → course path → Module 1 (read it, discuss it with a live tutor chat, or hear it as a custom two-host podcast) → applied activity with AI grading. Built as a credibility artifact for a single reviewer, not a product.

**Stack:** Cloudflare Workers (Hono) · Vite + React + TypeScript SPA served via Workers assets · D1 + Drizzle · Tailwind with all brand values as CSS custom properties · Anthropic API for grading, the module tutor, and podcast scripts (worker-side only) · Workers AI text-to-speech + R2 for podcast audio.

## Run it locally

```bash
npm install
npm run seed:generate        # prints the demo passcodes it hashed
npm run db:migrate:local
npm run db:seed:local
npm run build                # SPA → dist/client
npm start                    # wrangler dev on :8787
```

Demo passcodes (default seed): `OMNISSA-101` (omnissa brand) and `VERDANT-DEMO` (verdant brand). Override with `DEMO_CODES='brand:CODE:Label,…' npm run seed:generate`. Only PBKDF2 hashes (100k iterations, per-code salt) reach the database.

For SPA hot reload during UI work: `npm run dev` (Vite on :5173, proxying `/api` to wrangler on :8787 — run both).

Grading, the tutor chat, and podcast scripts need a key: create `.dev.vars` with `ANTHROPIC_API_KEY=…` and `SESSION_SECRET=…`. Without a key everything else works; submissions save with a graceful "grading unavailable" state, the tutor reports itself offline, and the podcast studio says so instead of generating.

Podcast audio uses the Workers AI binding (`@cf/deepgram/aura-2-en`), which proxies to your Cloudflare account even under `wrangler dev` — so with the `ai` binding in `wrangler.jsonc`, local dev needs `wrangler login` (or `CLOUDFLARE_API_TOKEN`) to start at all. Working fully offline? Temporarily remove the `ai` block from `wrangler.jsonc`: everything runs, and the podcast studio honestly degrades to transcript-only episodes. R2 is simulated locally; no bucket setup needed for dev.

## Deploy

```bash
wrangler d1 create fluency-demo        # paste the id into wrangler.jsonc
wrangler r2 bucket create fluency-demo-audio   # podcast audio cache
npm run db:migrate:remote
npm run seed:generate && npm run db:seed:remote
wrangler secret put SESSION_SECRET
wrangler secret put ANTHROPIC_API_KEY
wrangler secret put ADMIN_PASSCODE     # gates the operator console at /admin
npm run deploy
```

## Architecture notes

- **Content is data.** Module 1 lives as `fd_content_block` rows seeded from `content/module-1-blocks.json`, preserving the stable/volatile split from the source draft (`[V]` passages are separate `layer: 'volatile'` blocks with `dependsOn` watch topics). The module footer's `Concepts reviewed · Examples current as of` stamps are computed from `reviewedAt` minimums per layer — never hardcoded. The future maintenance agent patches volatile blocks only.
- **Brand is data.** One brand active per deployment (`BRAND_SLUG` var). A brand is one JSON file (`content/brands/*.json`) → `fd_brand` row → CSS custom properties applied at `:root`. Components only read `var(--c-*)` / `var(--font-*)` / `var(--radius)`. The throwaway `verdant` brand exists purely to prove the swap: set `BRAND_SLUG=verdant`, redeploy, zero component changes. Omnissa palette and type (Outfit, `#001E60` / `#4A12F0` / `#C9FF27`) were derived from omnissa.com, not guessed.
- **Access has two doors, one per deployment (`AUTH_MODE`).** The **demo door** (`passcode`, this deployment's default) is the shared passcode described below. The **product door** (`accounts`) disables passcode entry entirely: learners sign up with email + password (PBKDF2, same format as codes), and sign-up is **census-gated** — the email must be on the imported `fd_employee` roster, so the census is the allowlist and there is no open registration. Progress follows the account, not the browser: signing in reuses the account's canonical session, so a new device picks up exactly where the last one left off, and census matching upgrades from name-based to exact account-email identity. No email provider means no self-serve reset yet — the admin's Census tab issues a one-time temp password (shown once, never stored) and learners change it from the sign-in screen.
- **The demo door.** Shared passcode per brand, PBKDF2-hashed with per-code salt, constant-time comparison, verified server-side only. Success sets an `HttpOnly; Secure; SameSite=Lax` cookie holding an HMAC-SHA256-signed session id (30 days). Failed attempts are rate limited: 10 per IP hash per 15 minutes. IPs are stored only as salted SHA-256 hashes.
- **The funnel** is append-only in `fd_event`. One statement answers it end to end:

  ```sql
  SELECT type, COUNT(*) AS events, COUNT(DISTINCT session_id) AS sessions
  FROM fd_event GROUP BY type ORDER BY MIN(created_at);
  ```

- **The brand admin steers the AI.** The admin console's **Brand** tab edits the deployment's brand in place — company name, design tokens, voice, and which AI tools the org provisions (all data, per the "brand is data" rule above) — and carries **content guidance**: free text the company admin writes overall, per course, or per module (`fd_brand_guidance`). Guidance rides into every LLM personalization prompt alongside the module content — the tutor gets it in its cached system block, podcast scripts get it inside `<company_guidance>` in the module block — framed as points to emphasize and reinforce, complementing the content rather than replacing it. It's cache-safe (varies only by deployment and module, like the content itself), and guidance edits count as content changes, so stale stock episodes re-bake automatically.
- **The census closes the loop from roster to completion.** `fd_employee` holds who *should* be taking the course — name, email, role, manager, level, location, start date — imported via CSV in the admin's **Census** tab (tolerant header mapping, quoted fields, re-import upserts by email then name). Workday/Okta sync is designed to land on the same rows (`source` column) but is not yet connected. Learners are anonymous passcode sessions, so census rows match to sessions by self-reported intake name until SSO provides identity — the tab shows per-employee course status (not started / started / N modules done, last seen) and is honest about why an unmatched row might just be a name mismatch. The **Reminders** tab configures nudge rules (`fd_reminder_rule`): audience (employee or their manager), trigger (not started / inactive / started-but-incomplete), a day threshold, and a message template with `{name}`-style placeholders. A live preview renders exactly who each active rule would notify today with the filled-in message — the full evaluation path exists; delivery awaits an email provider and sends nothing yet.
- **Completion is auditable.** Because the course is dynamic — blocks get patched by the maintenance agent, exercises evolve, every podcast episode is personalized — a completion record alone can't say what the learner actually saw. So every completion moment writes an append-only `fd_completion_audit` row pointing at a content-addressed snapshot (`fd_content_snapshot`: SHA-256 of the exact serialized content; one row per distinct version no matter how many learners witness it). Captured server-side, never trusted from the client: module and micro reads (`module_viewed`/`micro_viewed`, deduped to one row per version per session, plus `module_completed` at the completion event), knowledge-check/sorting/choice submissions (the full exercise payload as it stood), activity submissions (the brief *and* the rubric that graded them, keyed to the submission id), and podcast listens (the episode's lines, outline, takeaways, and sketch as heard). Tutor transcripts and submission bodies are already stored verbatim (`fd_chat_message`, `fd_submission`), so they need no snapshot. The admin console's **Content audit** tab answers "who completed what, against which version" and opens the exact content as it stood — even after the live version has changed.
- **Personalization is the front door.** After the passcode, a five-step intake (name/role, how to start, time available, learning styles, free-text objective) writes to `fd_preference` and composes a deterministic plan (`GET /api/plan`) cut to the learner's time budget, echoing their objective and picking their starting point. Roadmap modalities (chat self-assessment, voice, podcast, course-as-MCP-server inside Claude/ChatGPT) appear as honestly tagged options — selecting one records demand in the funnel rather than faking a feature.
- **Calibration** (`fd_calibration`) carries the diagnostic baseline (`diagnostic:tN`), the full sorting exercise (`sort:tN`), and the Conversation-2 prediction (`m1:conversation2`). The result screen's signature visual renders from it.
- **The tutor chat** (`/module/1/chat`) turns a module's content into an interactive lesson. It is content-driven end to end: the worker loads whatever `fd_content_block` rows exist for the module and builds the tutor's system prompt from them, so seeding a new module's content file gives that module a working tutor with zero code changes (`GET|POST /api/module/:id/chat` refuses modules that aren't open or have no blocks). The persona teaches in lecturettes, asks one applied question at a time, runs quiz mode, and follows the learner's steer; a `<paths>a|b|c</paths>` trailer on every reply becomes clickable next-move chips in the UI (the worker holds streamed text back a few characters so the tag never flashes on screen). Learner context — name, role, stated objective, time budget, diagnostic calibration direction, sorting-exercise result — rides in a second system block, so the tutor opens personalized. Replies stream token-by-token over NDJSON from the worker (`CHAT_MODEL`, key never leaves the worker); the module content block carries a prompt-cache breakpoint shared across sessions, and the conversation tail carries a second one. The transcript persists per session per module in `fd_chat_message` (raw model output, including the trailer), user turns are saved before the model is called and partial replies are saved on mid-stream failure, so nothing is ever lost. Limits: 30 tutor replies per session per hour, 2,000 chars per message, last 40 turns sent to the model. Funnel events: `chat_started`, `chat_message` (with a `via: text|voice` marker), `chat_reset`.
- **Voice is an input mode, not a page.** Every open text box in the app — the tutor composer, the intake objective, the applied-activity submission, the podcast focus prompt — carries a mic button (`MicButton`): record, Workers AI Whisper transcribes worker-side (`POST /api/voice/transcribe`, 60 clips/hour/session, 8 MB cap), and the text lands in the box for editing. The tutor chat goes further with a **voice mode** toggle: the mic sends what you said straight to the tutor, and every reply is read aloud in the tutor's own voice (Aura `athena` — deliberately a third voice, distinct from the podcast hosts). Any assistant reply also has a Listen button; audio renders on first request (`GET /api/module/:id/chat/audio/:messageId` — markdown stripped to speakable text, chunked at sentence boundaries, stitched MP3) and caches in R2 under `chat-tts/`. The mic hides itself entirely on deployments without the AI binding or browsers without a mic API — typing is never degraded. Funnel events: `voice_transcribed`, `chat_audio_rendered`.
- **The podcast** (`/module/1/podcast`) is one made-for-you episode per module, not a studio the learner has to operate. The scriptwriter gets the module's content blocks (exercises excluded — you can't read JSON aloud) plus everything known about the listener — name, role, selected goals, investment depth, diagnostic direction — and is told to make the episode unmistakably theirs: greeted by name, examples fit to their role, goals addressed mid-episode, length set by their depth (quick/standard/deep). The show is **Fluent**: Maya knows the material cold, Leo asks what you would ask — deliberately against the curious-woman/expert-man trope. Every episode opens on the call sign with a beat of banter and a preview, and lands with a conversational recap of the takeaways, one thing to try, and Maya's verbatim sign-off ("Stay curious — and check the work.") — the ritual lives in `PODCAST_SHOW`, the humor is prompted deliberately (`podcast-v7` prompt, `PODCAST_MODEL` + prompt version persisted on `fd_podcast`). The script also carries a study layer: a 3–6 beat **outline** (`outline_json`) rendered as a follow-along rail beside a compact transcript — beats light up with playback and click-to-seek, both estimated by character proportion — plus 3–5 **key takeaways** (`takeaways_json`) and a **sketch** (`visual_json`): the study call first lists which ideas in the episode are inherently structural (a scratchpad `candidates` field, discarded), then models the ONE strongest in whichever of five shapes matches its actual structure — **flow** (process), **ladder** (levels), **hub** (factors feeding one thing), **quad** (2×2 tradeoff), **venn** (the intersection is the point) — or honestly returns null. Sketches render as hand-drawn charts in the Fosslien/West-Duffy comic-chart spirit: wobbly strokes (SVG turbulence displacement), slight box tilts, handwritten labels (bundled Caveat), brand tokens for color, and a required *"What to see"* insight caption. All layouts are deterministic — no graph library. The study companion is **client-driven**: the page POSTs `/api/podcast/:id/study` in parallel with the audio fetch and slots the cards in when it returns (pregen fills it server-side; `STUDY_MODEL` var optionally upgrades just this call). Q&A segments get takeaways; their sketch is usually null by design. All of it is best-effort — malformed extras degrade to null, never to a rejected episode. **The instant layer:** personalization moves earlier in time. Per module (baked lazily, self-healing on content change): a **stock episode** — intro previewing the module's fixed beats + a full fallback body — plus the study assets, voiced into R2 (`fd_podcast_stock`, `podcast_stock_baked`). Per goal: a flavored intro variant, baked the first time a learner holds that goal. Per learner, at intake and each `module_completed`: a tiny **personal intro** — name, role, goals in natural speech — voiced in the background (`fd_podcast_intro`, `podcast_intro_ready`). Arrival then creates an **assembled episode instantly**: the best available pre-voiced intro (personal > goal > generic) starts playing at once with stock study cards already on the page, while the **custom body** writes in the background (`writeCustomBody` gets the intro verbatim plus the fixed beats; every intro ends with Leo teeing the first beat as a question and every body opens with Maya answering it — that engineered seam is what makes the splice inaudible). The chunk route briefly holds for the body on young episodes; if the writer fails, the stock body (lines + copied audio) completes the episode. First visitor to a module before any bake gets the legacy full-script path once, and the bake runs behind them. Podcast-pickers still get the whole episode — body and voices — pregenerated before arrival. Timing is measured end to end: `podcast_started` (with `introSource`) → `podcast_body_ready` (ms) → client-posted `podcast_first_audio` (ms from open to sound). After listening (gated server-side on `podcast_played`), the learner can **ask the hosts questions**: a `kind: 'qa'` follow-up segment (quick length, mailbag format, grounded in the module, questions inside `<listener_questions>` tags as steering data, not instructions). The Q&A hosts also remember what this listener actually heard: the module episode's script and the last three follow-ups ride along in `<heard_episode>` blocks, so answers can point back to the exact episode ("like we said about…") and build on earlier answers instead of repeating them. One default episode per module; free-form regeneration is gone. **Audio streams in chunks:** the script is cut at speaker-turn boundaries into ~5 parts (the first ~10% of the speech, so playback starts in seconds — `shared/audioChunks.ts`, one deterministic plan shared by worker and player). The background render (`waitUntil` after every script, manual or pregenerated) fills the R2 cache with **all chunks rendering concurrently** — wall time is the slowest chunk, not the sum — and the chunk route briefly waits for an in-flight background render on young episodes before duplicating it live. The first chunk is ~15% of the speech (about a minute of runway) and the player prefetches two chunks ahead. Module content rides as a cache-controlled system block on script and study calls (cross-session Anthropic prompt caching). **Two voice engines:** with the optional `GEMINI_API_KEY` secret set, chunks are voiced by Gemini's native multi-speaker TTS (`GEMINI_TTS_MODEL`, default `gemini-3.1-flash-tts-preview` — the NotebookLM tech family: the whole chunk's dialogue in one call, both voices sharing prosody, no stitching seams; raw PCM wrapped in a WAV header worker-side, ~10–30¢/episode), with Workers AI `@cf/deepgram/aura-2-en` (thalia/orpheus, $0.03/1k chars) as the per-call fallback and the only engine otherwise. Chunks store their content type in R2 metadata and the player is format-agnostic per chunk, so mixed-engine episodes still play. The `podcast_audio_rendered` event records which engine voiced each render; the player fetches chunk 0 immediately — served from cache or voiced live in ~10–20s, whichever wins — then chains parts gaplessly at turn boundaries, always fetching one ahead. There is no polling and no whole-episode wait anywhere. Custom controls: play/pause, char-proportion progress bar with click-to-seek, elapsed/total (estimated until all chunks load), and a playback-speed cycle (1×/1.25×/1.5×/2× — persisted per browser). Episodes voiced before chunking keep their single cached MP3 (`audioMode: 'single'`). No key → honest offline message; no AI binding → transcript-only. Scripts/hour/session are capped by the `PODCAST_LIMIT_PER_HOUR` var (default 4, set to 12 for demo testing), covering manual, Q&A, and pregeneration alike. Funnel: `podcast_requested` (with `kind` + `trigger: manual|pregen`) `→ podcast_script_ready → podcast_audio_rendered → podcast_played`.
- **The course is an MCP server** (`/api/mcp`, worker-side in `src/worker/mcp.ts`). Stateless streamable HTTP — JSON-RPC in a POST, JSON back, no SDK dependency — so Claude (custom connector), Claude Code (`claude mcp add --transport http`), and ChatGPT (developer-mode connector) connect with nothing but a URL. **Two credentials open it, and both resolve to one `fd_session`** — so progress made inside an assistant and progress made in the app are literally the same record. (1) **OAuth 2.1** (`src/worker/oauth.ts`), which is what the claude.ai "Connect" button requires: it will not accept a pre-authenticated URL, it probes the endpoint, expects a `401` whose `WWW-Authenticate` names protected-resource metadata, and runs the whole handshake. So this deployment is its own authorization server — RFC 9728 resource metadata at `/.well-known/oauth-protected-resource` (both bare and path-inserted), RFC 8414 server metadata at `/.well-known/oauth-authorization-server`, RFC 7591 dynamic client registration at `/oauth/register` (no manual client provisioning — Claude registers itself), and PKCE-required `S256` authorize/token endpoints. The trick that keeps it simple: the learner is *already* authenticated here, so `/oauth/authorize` never collects credentials — it renders a **branded consent screen** (server-side HTML using the deployment's own brand tokens) listing exactly what the assistant will be able to do, and on approval mints a token bound to their existing session. No session yet? It routes through the course's own door (`/enter?next=…`, validated against an open-redirect) and comes straight back. Tokens are opaque, stored only as SHA-256 hashes, 8-hour access with 30-day **rotating** refresh; a reused refresh token or a replayed authorization code revokes that client's whole token family. Redirect URIs match exactly (loopback http allowed for local clients, ports ignored per RFC 8252; cleartext elsewhere and script-capable schemes rejected), the RFC 8707 `resource` parameter is checked against this origin, and `/oauth/revoke` makes "disconnect" real. Because connectors run in a browser, every endpoint carries CORS with `WWW-Authenticate` in `Access-Control-Expose-Headers` — without that the challenge is invisible and discovery silently fails. (2) The original **personal signed key in the URL path** (`/api/mcp/<key>`, session id HMAC-signed under an `mcp:` domain so it can never be replayed as a session cookie) remains for clients that don't speak OAuth and for command-line testing. `GET /api/mcp/connection` returns both: `url` (plain, non-secret, the one to paste) and `keyUrl` (a secret, behind a disclosure on the setup page). Note both `/.well-known/*` and `/oauth/*` must be listed in `run_worker_first` — otherwise the SPA asset handler answers discovery with `index.html`. Six tools: `get_course_overview` (TOC + live progress + who the learner is), `get_module` (the full teaching package — content blocks with variants resolved, key takeaways and the concept sketch from the module's baked stock study assets, links to the in-app podcast/check/activity, and per-learner tutoring guidance), `get_knowledge_check` (questions **without keys** — the assistant administers, it never grades), `submit_knowledge_check` (server-side grading against `fd_exercise`, logs the same `knowledge_check_submitted` event the app writes, so a pass earned in Claude clears prerequisites on the path screen), `complete_module` (server-verified: witnessed engagement plus a 60%+ check pass required; writes `module_completed`, the completion-audit snapshot, and fires the next module's podcast pregeneration — same hooks as the app), and `recommend_next` (ranked options with legible reasons from the learner's goals, diagnostic direction, and course order). Eight more tools make the connection a full learning surface rather than a reader: `apply_to_my_work` (the connector's unfair advantage — the module's frameworks worked on a real task from the learner's chat, with the assistant coached to ask the framework's questions instead of doing the task), `record_prediction` (the course's calibration thread over MCP — free text plus rubric-declared numeric opening fields into `fd_calibration`, closed later by the activity's `actualFor` fields), `submit_teach_back` (Feynman mode: the learner's own-words explanation graded server-side by the existing rubric grader against the module's actual key points — three fixed dimensions, 5/hour budget), `get_scenario_challenge` + `submit_scenario` (the sorting engine as a conversational game: scenarios staged as live workplace moments, every call committed before the reveal, scored by the shared `scoreSortingSubmission` core with `also`-arguable placements honored and the same calibration rows written), `get_activity` + `submit_activity` (the real graded capstone path — the extracted `submitActivityCore` the app endpoint itself runs, so save-first, audit pack, calibration closing, rate limit, build-so-far grading context, and review-desk visibility are identical from either surface), and `ask_the_hosts` (a Q&A follow-up from Fluent's hosts via the extracted `createQaEpisodeCore`: same listened-first gate and hourly limit, transcript returned to the chat while the audio renders for the app). Five prompts (`learn`, `quiz`, `challenge`, `apply`, `whats-next`) appear as slash commands in clients that surface them. The server's `instructions` field carries the tutor persona — same voice contract as the in-app chat tutor — so a connected assistant behaves like the course's tutor, not a search box over course files: lecturettes, one applied question at a time, completion earned not claimed. Funnel events: `mcp_oauth_approved`, `mcp_connected`, `mcp_tool_called`, `knowledge_check_started`, and the shared `module_opened`/`knowledge_check_submitted`/`module_completed` with a `via: 'mcp'` marker.
- **The operator console** (`/admin`, unlinked) is gated by the `ADMIN_PASSCODE` secret and a separate HMAC-signed cookie; login attempts are rate limited like passcodes. Six tabs: **learners** (the LMS completion log — per-learner roster with first/last seen, estimated active time computed from gaps between recorded interactions capped at 10 minutes, modules completed, latest-attempt quiz averages, best activity score, podcast listens; drill into any learner for their full timeline, submissions, and the content versions they witnessed), **content** (browse every module's reading/micro/activity blocks with variant and layer tags, and edit block bodies in place — edits go live for new views while earlier learners keep their audited snapshot, and each edit stamps `reviewedAt` and logs `content_block_edited`), a **review queue** (read any submission, add operator reviews with an optional /20 score — the async backup path for AI 201's peer exchange, per `fd_review`), **reporting** (totals, the full funnel, goal/style demand signals from intake, diagnostic calibration aggregates), **access codes** (list/create/disable; new codes are PBKDF2-hashed server-side and usable immediately, plaintext never stored), and the **content audit** trail described above. With the secret unset, admin login returns 503 and the rest of the app is unaffected.
- **Grading** calls the Anthropic API from the worker (key in `wrangler secret`), rubric dimensions verbatim in the system prompt, strict-JSON response parsed defensively with one retry, then a graceful "saved, grading unavailable" fallback — submissions are persisted *before* grading is attempted, so nothing is ever lost. 5 grading calls per session per hour. `model_used` and `prompt_version` persist on `fd_submission`. Calibration is explicitly graded on honesty and specificity, not accuracy.

## Scope (v1, deliberate)

Accounts exist but the demo runs the passcode door (`AUTH_MODE`); no SSO yet — Okta lands with the census integration project. Modules 2–8 and courses 201/301/401 are locked cards with real titles and blurbs (full 201 module drafts live in `content/ai201-*.md`). No gamification, no multi-tenancy, no SCORM. The admin console serves one company admin per brand deployment.
